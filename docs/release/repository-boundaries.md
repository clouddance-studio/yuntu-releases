# 仓库与交付边界

结论：当前不必新建 Git 仓库。先用现有 `clouddance-studio/yuntu-releases` 完成一个可核对的发布资料与用户接入入口，避免 Skill、MCP、使用指南分散后版本无法对应。

| 位置 | 当前职责 | 不放什么 |
| --- | --- | --- |
| `yuntu-releases` | 英文介绍、Release 使用说明、发布记录、用户 Skill、可单独运行的 MCP 桥接脚本及来源、本地最终产物归档 | 编辑器主体源码、后台源码、凭据、生产数据、内部开发 Skill |
| `clouddance-website` | 公司首页、`/yuntu/` 产品与 `/yuntu/docs/` 帮助；后续链接真实下载／支持／隐私入口 | 安装包开发构建、私人连接文件、伪造已上线链接 |
| 编辑器源码仓库 | 构建、打包、正式 API 与 MCP 实现真源及内部开发 Skill | 不直接作为普通用户安装前置 |
| 账号后台与基础设施仓库 | 账号服务和基础设施实现 | 不为发布文档而公开源码或生产配置 |

`integrations/mcp/` 只准备两个明确可交付的外部连接脚本和针对它们的协议测试；保持与来源文件一致，并记录 SHA-256 及来源提交。不把私有源码仓库路径当作用户运行依赖。`integrations/skills/yuntu-editor/` 为独立英文使用 Skill，不复制 `rust-ui-editor-dev`。

后续只有出现独立维护和授权需求时再拆仓库：

- `yuntu-mcp`：桥接形成独立安装包／包管理器发布、版本兼容和 CI 维护时。
- `yuntu-examples`：出现多个可复用、已授权的完整示例，需要社区单独贡献时。
- `yuntu-generators`：官方公开生成器形成独立源码、授权、测试和版本周期时。

这些名称只是未来预留建议，本轮没有创建远程仓库。当前 `release/1.0.0-beta.3` 是本地审阅分支，不合并用户确认的主分支 `main`，不推送或创建远程 tag／Release。
